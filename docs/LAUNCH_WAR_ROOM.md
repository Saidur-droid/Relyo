# Relyo V2 — Launch War Room

> **STATUS: ACTIVE LAUNCH OPERATING PLAN**

## Objective

Coordinate product, support, content, community, metrics, and partnerships during public launch windows.

## Launch principle

Do not launch because a date arrived. Launch when the user can experience the core magic:

```text
Check My App
→ meaningful app-specific finding
→ Verify My Launch
→ inspectable Passport
```

## Launch readiness checklist

Product:

- landing page live;
- URL check stable;
- repo connect stable;
- proof results understandable;
- Passport share page functional;
- pricing/checkout functional;
- analytics events verified;
- error handling/support path visible.

Trust:

- no absolute safety claims;
- evidence scope/exclusions visible;
- secrets/logging reviewed;
- incident escalation owner known;
- false VERIFIED escalation process tested.

Growth:

- launch posts prepared;
- demo video prepared;
- founder thread prepared;
- Product Hunt assets prepared if used;
- Hacker News post drafted if appropriate;
- partner/community outreach scheduled;
- 100 Apps Verified application live;
- referral link/credits ready.

## Channel plan

### Product Hunt

Use only when free product demonstrates value immediately.

Launch assets:

- clear title;
- 30–60 second product video;
- screenshots of Check My App → Passport;
- founder story;
- launch checklist resource.

Do not manufacture votes.

### Hacker News

Best angle:

- technical build story;
- open Proof Contract spec;
- independent verification architecture;
- useful free tool.

Avoid marketing fluff.

### X / LinkedIn

Founder narrative:

1. software creation has become dramatically faster;
2. launch risks still exist;
3. Relyo checks critical flows;
4. live proof demo;
5. invite founders to 100 Apps Verified.

### YouTube / short-form video

Content:

- 30-second “check this before launch” clips;
- full live proof demos;
- founder case studies;
- technical Proof Contract explainers.

### Reddit / communities

Only participate where relevant and transparent.

Lead with useful checklist/data; disclose founder affiliation.

### Press

Pitch only after evidence exists.

Potential story angles:

- new launch-verification behavior for AI-built software;
- aggregate production-readiness data;
- open proof standard;
- builder-neutral trust infrastructure.

## Daily war-room dashboard

Track hourly/day-of:

- qualified visitors;
- free checks started/completed;
- repo connections;
- meaningful findings;
- proof runs;
- purchases;
- Passports issued;
- share/referral traffic;
- error rate;
- queue latency;
- proof cost;
- support tickets.

## Launch response rules

If traffic spikes:

- preserve proof correctness over speed;
- queue expensive checks;
- degrade nonessential visuals/features, not evidence integrity;
- show accurate wait/status messaging.

If provider fails:

- mark proof UNKNOWN/PARTIAL where appropriate;
- do not convert inability to verify into PASS.

If public criticism is valid:

- acknowledge specific issue;
- fix product/process;
- publish technical correction when useful.

## Referral incentives

Early safe options:

- proof credit;
- re-check credit;
- subscription credit.

Avoid cash referral until abuse controls exist.

## Post-launch 72-hour review

Review:

- top acquisition sources;
- top activation drop-offs;
- support burden;
- price objections;
- false positives;
- proof failures caused by Relyo itself;
- most shared Passport types;
- highest-converting launch moment;
- partner inbound;
- content resonance.

Ship fixes immediately for top activation blockers.

## Post-launch 14-day review

Decide:

- which channel deserves more investment;
- which pricing variant wins;
- which proof contracts users value most;
- whether 100 Apps Verified is generating referrals;
- whether agency/builder motion is stronger than direct founder acquisition;
- whether product should narrow further.

## War-room success definition

A launch is successful only if it creates **retained verified apps and paid/repeated proof**, not press or traffic alone.
