## Core Mission

Relyo is the **independent proof layer for machine-built software**.

> **AI builds it. Relyo proves it.**

Relyo does not need to beat Lovable, Replit, Cursor, Codex, Claude Code, model labs, clouds, or specialist security/observability vendors.

The strategic goal is neutral proof infrastructure those systems are better off using.

## P0 MARKET RULE — OWN THE LAUNCH MOMENT

Users do not initially purchase “software proof infrastructure.” They purchase confidence when failure can cost money, customers, credibility, or a deal.

Relyo must prominently own:

1. **Verify Before Launch**
2. **Verify Before Charging Customers**
3. **Verify Before Investor Demo**
4. **Verify Client Delivery**
5. **Verify Latest Release**

Default acquisition path:

```text
high-intent moment
→ Check My App Free
→ app-specific finding
→ Verify My Launch / relevant proof mode
→ Production Passport
→ recurring proof / agency / API / partner expansion
```

Do not hide these moments behind assurance jargon on first contact.

## Evidence-Led Category Education

Most early users know symptoms, not the category name.

Relyo must teach the need through credible evidence, practical checklists, app-specific findings and proof.

Never attack or reduce the credibility of Lovable, Replit, Cursor, Codex, Claude Code, Vercel, Supabase or other builders/providers.

Correct framing:

> **AI builders make software creation dramatically faster. Production still has universal engineering risks. Relyo helps users verify the critical outcomes before customers depend on them.**

Public statistics must be sourced, dated, caveated, and separated from Relyo’s own data.

## Hypergrowth Objective

Relyo may pursue an extremely aggressive 6–12 month breakout, but valuation is never guaranteed or treated as an engineering requirement.

The objective is:

> **Create enough product, usage, growth, revenue, platform adoption, trust, and network evidence that credible investors can believe Relyo can become the universal proof layer for machine-built software.**

Do not optimize for press, raw scans, or vanity valuation without retained proof usage.

## Trust-Network Rule

Relyo must create value for both software producers and proof consumers.

```text
software producer
→ Relyo Proof Network
→ proof consumer
→ real outcome intelligence
→ Verified Failure Graph
→ better proof for next release
```

Software producers include AI builders, coding agents, human teams, agencies and internal enterprise agents.

Proof consumers include founders, enterprises, buyers, investors, marketplaces, procurement systems, auditors, insurers, clouds, agencies and future autonomous systems.

The strongest long-term network milestone is third parties consuming Production Passports they did not themselves create.

## Product Principles

Every major implementation decision must preserve:

- provider-neutral architecture;
- independent verification of outcomes;
- evidence-backed verified states;
- scoped attestations rather than absolute safety claims;
- explicit unknown/exclusion handling;
- safe automation with approval gates;
- rollback before risky changes where feasible;
- least privilege;
- plain-language founder UX;
- business journey verification, not only infrastructure checks;
- continuous proof after launch;
- cost and recovery as first-class concerns;
- privacy-preserving operational learning;
- creator/fixer/verifier separation where practical;
- API-first provider control, browser automation only when needed;
- deterministic final status outside free-form model judgment.

## AI Moat Doctrine

The LLM is not the moat.

Models may help discovery, planning, diagnosis, explanation and remediation generation. They must not unilaterally decide final VERIFIED state.

The central AI/data moat is the **Verified Failure Graph**:

```text
producer family
+ stack fingerprint
+ release change
+ contract attempted
+ failure class
+ root cause
+ repair class
+ independent verification result
+ regression result
+ cost/latency
```

Core rule:

> **AI reasons. Evidence decides.**

Do not expose private customer code or secrets to create network value.

## Assurance Model

Use:

- `R0` — Discovered
- `R1` — Launch Verified
- `R2` — Business Verified
- `R3` — Resilience Verified
- `R4` — Continuous Proof

Every proof state must expose:

- exact release/environment;
- contracts executed;
- evidence references;
- verifier identity/version;
- freshness/expiry;
- exclusions/unknowns.

Never claim absence of all defects or “100% safe.”

## Trust Kernel Rule

The codebase now includes an initial `packages/kernel` TypeScript package.

Important behavior:

- contract evaluation is deterministic;
- UNKNOWN cannot become PASS;
- assurance promotion requires level-specific proof requirements;
- passports are bound to release/environment/verifier.

A CI test caught an initial assurance-promotion bug where lower-level contracts could incorrectly promote to R4. That bug was fixed. Preserve this quality bar: **tests should catch trust inflation.**

## Risk Classification

Every production action must be one of:

- `OBSERVE`
- `SAFE_REVERSIBLE`
- `APPROVAL_REQUIRED`
- `HUMAN_ONLY`
- `FORBIDDEN`

High-risk flow:

```text
observe
→ calculate blast radius
→ create rollback/restore point
→ stage/shadow test where possible
→ obtain approval
→ smallest change
→ independently verify
→ revert if proof fails
```

## Definition of Done

A task is not complete because code compiles, a PR merges, deployment says READY, or an agent reports success.

Where applicable, done requires:

1. implementation;
2. automated tests;
3. security/threat review;
4. failure-path handling;
5. explicit risk classification;
6. evidence collection;
7. independent verification;
8. rollback/recovery behavior;
9. metrics/observability;
10. documentation;
11. API/headless surface when strategically relevant;
12. Proof Contract or contract impact;
13. launch-moment UX impact where relevant;
14. growth/distribution path where relevant;
15. shareable output where relevant;
16. Verified Failure Graph telemetry impact where policy allows;
17. continuity update.

A user-facing capability that cannot explain how users discover it, activate it, pay for it, share it, or return to it should be questioned.

## Runner & Credential Security

Prefer:

- isolated runners;
- outbound-only connectivity where feasible;
- provider-native OAuth/app installations;
- short-lived credentials;
- scoped capability tokens;
- customer KMS/private-runner options;
- secrets excluded from model context;

## Metrics Discipline

Do not optimize primarily for scans, integrations, press coverage, or dashboard MAU.

Track:

### Launch-moment funnel

- visitor → free check;
- free check → meaningful finding;
- finding → proof start;
- proof start → paid;
- Launch Proof → Continuous Proof.

### Virality

- Passport share rate;
- Passport visitor → new check;
- agency/client propagation;
- partner-sourced apps.

### Product / Trust

- Verified Production Outcomes;
- verified releases;
- verified critical journeys;
- time to R1/R2;
- false VERIFIED rate;
- remediation/rollback success;
- cost per proof.

### Platform / Network

- external API/MCP-initiated proof %;
- builder integrations;
- third-party Passport consumers;
- releases gated by Relyo policy.

The false VERIFIED rate is sacred. Drive it toward zero.

## Weekly Operating Cadence

Every week answer:

1. Which launch moment produced the most qualified demand?
2. What blocked users from an app-specific finding?
3. Which finding converted best to paid proof?
4. Which Passport was shared and why?
5. Which partner can distribute Relyo to many apps?
6. Which contract reduces time-to-value most?
7. What did the Verified Failure Graph learn?
8. Did proof cost/gross margin improve?
9. What lowered false-pass probability?
10. What work created no proof or distribution value?

Every week should improve at least one:

```text
launch-moment conversion
proof depth
activation speed
shareability
partner distribution
failure intelligence
trust/security
proof economics
```

## Roadmap Discipline

Before a large feature, answer:

1. Does this strengthen a launch moment?
2. Does it improve independent proof?
3. Does it improve evidence portability/shareability?
4. Does it make a builder/platform/agency more likely to distribute Relyo?
5. Does it create Verified Failure Graph intelligence?
6. Does it improve proof economics?
7. Could a specialist product supply this better than Relyo rebuilding it?

Avoid generic capabilities better supplied by builders, clouds, AppSec, observability, testing, browser automation, or infrastructure vendors.

## Continuity Rule

At the end of meaningful work, update repository documentation, issues, roadmap state, ADRs, or execution status so the next developer/agent can continue without chat history.

For active implementation sessions, keep `WORK_PROGRESS.md` current at meaningful checkpoints, not only at the end.
